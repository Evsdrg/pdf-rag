# 设计：按模型分区的向量存储

状态：**第一、二、三步均已实施**（见 §7）；分区向量索引已补上（§5.1）。
目标读者是后续实现者与评审者。

- 第一步（结构就绪）：主表去 vector 列、uid、单分区、检索改走分区+回表 —— 已上线
- 第二步（多模型与选择）：优先级/排除、`--rebuild-vectors`、覆盖率降级 —— 已上线
- 第三步（打包与界面）：bundle 带分区清单、导入按本地可用分区判断、资料库页展示覆盖率 —— 已上线
- 追加（性能）：分区向量索引 `IvfFlat` + `refine_factor`，生产 59.9ms → 32.8ms —— 已上线

## 1. 要解决的问题

当前索引把向量和元数据放在同一张 `chunks` 表的一个 `vector` 列里，隐含一个硬约束：
**整个索引只能有一个嵌入模型**。换模型就必须全量重建（12421 块约 15 分钟到 2 小时，
取决于上游限流），期间要维护影子库、切 `DB_PATH`，且无法回滚。

这挡住三类真实场景：

1. **用户的嵌入模型不稳定**。免费/公益服务经常限流或换渠道，用户手里可能同时有几个
   可用的模型（不同厂商、不同维度、不同质量）。现在只能绑死一个。
2. **换模型要能只做增量**。换到新模型后，应当只给"新模型还没有向量"的块补算，
   而不是把整个语料重算一遍——尤其是只改了几个文件的时候。
3. **多模型产出可以结合使用**。不同块可以用不同模型向量化，检索时按用户指定的
   优先级选用，而不是"非此即彼"。

非目标（明确不做）：

- 不在**同一次距离计算**里混合不同模型的向量。不同模型的向量空间不可比，
  混算得到的相似度没有意义。
- 不为每个模型单独建 FTS 索引。FTS 与模型无关，留在主表即可。

## 2. 核心模型

**一个块一个模型**是数据的粒度；**一个模型一个分区**是存储的粒度。

- **主表 `chunks`**：元数据 + 文本（`text/file/page/category/model_no/c_id/version/title/md5/uid`）。
  **移除 `vector` 列**。FTS 索引留在 `text` 上，天然与模型无关。
- **分区表 `vec_<slug>`**：`(uid, file, page, category, md5, vector[d])`。
  每模型（含 input_type 区分，见 §2.1）一张，**可以只覆盖部分块**。
- **`uid`**：跨表稳定标识。构造为 `file\x00page\x00块序` 的哈希。
  - 不能用 `file+page+text`：实测现有数据按此法生成有 **9 个碰撞**（8561 块），
    原因是同页存在逐字相同的块。
  - 用 `file+page+块序` 即可保证唯一：块序是提取阶段的确定性输出。
  - 提取是确定性的，未变更文件的 uid 稳定；文件内容变了则 md5 变、整文件重写。

分区表冗余存 `file/page/category/md5` 是为了把过滤下推到分区，避免
"先检索再回表再过滤"的低效（实测带 `category` 过滤的检索 37.9ms，可接受）。

### 2.1 分区标识：模型 + 维度 + input_type

分区 slug 必须完整标识**产生这批向量的调用契约**，因为任一要素不同都会产出
不同空间的向量，混用即不可比：

```
slug = <model>__<dim>__<input_type_doc>
例:  qwen3_embedding_8b__768__
     embed_v5_0_pro__2048__search_document
```

- **model**：模型名，`/`、`.`、`-` 归一为 `_`。
- **dim**：输出维度（`embed_dimensions`）。同一模型不同维度（MRL 截断）也是不同空间。
- **input_type**：`embed_input_type_doc`（建库侧）。Cohere 系同一模型用
  `search_document` 与留空产出不同向量；`input_type` 不同必须视为不同分区。
  留空时 slug 尾部为空段，保持可读。

**为什么必须区分 input_type**：它是嵌入契约的一部分——建库用 `search_document`、
查询用 `search_query` 时才是配对空间。若两个分区只按模型名区分，把 A 契约建的分区
与 B 契约的查询向量配对，检索会静默变差。查询侧因此需要**成对**选择：
选定某分区后，查询必须使用该分区记录在 `meta` 里的 `input_type_query`。

分区表自身带一行元数据（小表 `vec_meta` 或分区表的 schema metadata）：

| 字段 | 用途 |
|---|---|
| `slug` | 分区标识 |
| `model` / `dim` / `input_type_doc` / `input_type_query` | 复现查询向量所需契约 |
| `base_url` | 建库时的服务地址（仅供排查，不用于请求） |
| `created_at` / `updated_at` | 运维排查 |
| `blocks` / `files` | 覆盖量（写入时维护，避免每次全扫） |

## 3. 行为定义

### 3.1 增量是默认行为

`backend.ingest` 默认：只处理 md5 变化的文件，且**只写入当前现役模型的分区**。
其他模型的分区不受影响。换模型后点"增量索引"，效果就是"只给新模型缺失的块补向量"。

### 3.2 全量重建是显式操作

新增独立入口，语义与现有 `--rebuild`（重建主表）区分开：

```
--rebuild-vectors <model>   对指定模型重算全部块的向量
```

默认**保留**旧数据（同 uid 覆盖写入，等于替换）。配套开关：

```
--drop-old-vectors          重建前清空该模型分区（默认关闭）
```

"该模型分区"指 `--rebuild-vectors` 的目标模型，也就是当前 `embed_model` 对应的那一个；
**其他模型的分区一律不动**。要清理某个模型的分区，只能先把它设为当前模型再重建。

默认关闭的理由：清空是破坏性操作，且多数情况下覆盖写入已经达到目的；
只有需要清理"已删除文件的残留向量"时才需要清空。

### 3.3 查询期模型选择

两个配置项（进 `SPECS`，可在设置页改、即时生效）：

| 配置 | 含义 |
|---|---|
| `vector_models_priority` | 逗号分隔的模型优先顺序。一个块若有多个模型的向量，按此顺序取**第一个存在的**。 |
| `vector_models_exclude` | 逗号分隔的排除列表。被排除模型名下的块，若无其他模型向量，则不参与向量通道。 |

语义要点：

- **每次检索只用一种模型**（对某个块而言）。优先级决定用哪个，绝不混算。
- 一个块可能在多个分区里都有向量（用户先后用不同模型索引过同一批文件）。
  优先级让用户能说"优先用 A，A 没有再用 B"。
- 排除的块仍可被 FTS / 型号子串通道召回——向量通道缺失不等于该块不可检索。
- 优先级列表里的模型若某块全都没有，该块不参与向量通道。

### 3.4 部分覆盖必须响亮降级

分区没填满时，向量通道只在子集上召回，候选池变小，**质量会静默下滑**。
这与"向量维度不符"是同一类风险，处理方式也应当一致：

- 向量通道检测到覆盖率低于阈值（建议 100%，或显式配置）时，
  写入 `degraded` 并在日志里明确说明哪个模型、覆盖多少、缺多少块。
- `/api/stats` 暴露每个模型分区的覆盖率（已覆盖块数 / 主表块数）。
- 设置页在切换现役模型前校验覆盖率，不足时警告。

### 3.5 覆盖率口径：按块

**覆盖率一律按块统计**，因为向量化调用的输入单位就是块，不是文件：

- `embed_file()` 对文件的每个块单独取向量，一次 `/embeddings` 请求携带 N 个块的文本
  （`input` 是文本数组），返回 N 个向量，逐块落库。
- 因此"某文件有没有向量"不是全有或全无——限流中断、批量重试、按块补算都可能
  造成**同一文件部分块有向量**。按文件统计会把这些情况四舍五入成"有"或"没有"，
  掩盖真实缺口。
- 覆盖率定义为：

```
coverage(partition) = |{uid ∈ partition} ∩ {uid ∈ chunks}| / |{uid ∈ chunks}|
```

  分子分母都是块数。孤儿 uid（主表已无）不计入分子。

**为什么同时报告文件数**：文件数更适合展示给人看（"287 份文档，其中 12 份尚未
向量化"），也是增量索引的调度单位。所以 `/api/stats` 两个都报，但**降级判定
只看块覆盖率**——向量通道的召回能力由块数决定。

| 指标 | 用途 |
|---|---|
| `blocks_covered / blocks_total` | **降级判定**（决定向量通道是否可信） |
| `files_covered / files_total` | 展示与增量调度参考 |
| `files_partial` | 部分覆盖的文件数（有向量块 < 该文件总块数）——最需要人关注的信号 |

## 4. 技术可行性（已实测）

以下均在 LanceDB 0.36 + 现有 8561 块索引副本上验证，非推测：

| 能力 | 结果 |
|---|---|
| `table.drop_columns(["vector"])` | 5ms；**FTS 索引与查询完好**（`text_idx` 保留、检索正常） |
| 分区表 12421 块 768 维体积 | 38.4 MB |
| `WHERE uid IN (...)` 回表（300 个 uid） | 6 ms |
| 分区表带 `category` 过滤的向量检索 | 37.9 ms（主表平面检索 21ms，同量级） |
| 同库内 768 维与 1024 维分区并存检索 | 各自正常 |
| 分区按 `file` 删除 | 正常（12421 → 12377） |
| 分区中存在主表已无的孤儿 uid | **自然跳过**，不报错 |
| 覆盖率统计（扫分区 `file+md5`） | 13.3 ms |
| uid 生成 8561 块 | 89 ms（唯一 8552，见 §2 的碰撞说明） |

**两条被否决的路线**：

- **同表加多个向量列**：`add_columns` 只接受 SQL 表达式，且明确不支持
  `FixedSizeList`（报错原文只允许 `Int32`/`Timestamp` 等标量类型）。加一个模型就得
  整表重建，失去意义。
- **`db.rename_table`**：LanceDB OSS 版不支持（`not supported: rename_table is not
  supported in LanceDB OSS`）。需要换名时用"建新表 + 写入"替代。

## 5. 查询路径

```
search(query):
  fts       -> 主表 text 索引              -> 候选(含 uid)
  substring -> 主表 text 列                -> 候选(含 uid)
  vector    -> 按 priority 选分区组
               for 每个分区组:
                 // 查询向量必须用该分区的契约:model + dim + input_type_query
                 分区上向量检索(带 category/file 过滤) -> 命中 uid
                 (分区有向量索引时追加 refine_factor,见 §5.1)
               uid IN (...) 回主表取元数据/text
               (主表已无的 uid 自然丢弃)
  -> RRF 融合(候选统一按 uid 归并) -> 去重 -> 重排 -> 片段
```

### 5.1 分区向量索引

分区表建 `IvfFlat(nlist=16)` 索引,查询侧配 `refine_factor=2`。索引是**可选加速**:

- 没有索引的老库照样能查,退化为全表暴力扫描(结果同样精确)
- 查询侧只在 `has_vector_index()` 为真时才加 `refine_factor` —— 对暴力扫描加强化行为未定义
- 写入路径(增量 / `--rebuild-vectors`)与迁移脚本建完分区后自动建索引;
  **增量必须重建**:新写入的片段已有索引覆盖不到
- 补建入口 `python tools/build_vec_index.py`

`refine_factor` 不能省:IVF 只搜最近的一小部分簇,真实近邻可能落在没搜的簇里,
表现为静默漏召回。实测 rf=1 时 400 条查询漏 17 条,rf=2 漏 0 条。

`MIN_ROWS_FOR_INDEX = 4096`:低于该行数拒绝建索引。Lance 的 KMeans 在小数据上产出
大量空簇,实测 40 行建索引后 top10 与暴力扫描**无一相同** —— 这是正确性保护,
不只是性能取舍。

参数与实测数据见 `BENCHMARKS.md` §4.3。

**查询向量与分区必须成对**：选定分区后，查询侧用该分区 `vec_meta` 里记录的
`model + dim + input_type_query` 生成查询向量，而不是用当前全局配置。否则会出现
"用 A 契约的查询向量检索 B 契约建的分区"，相似度无意义。

三者缺一不可，**`model` 是最容易漏的一个**：只覆盖 dim/input_type 时，若两个模型
维度恰好相同（都截断到 768 这类情况很常见），维度校验通不出任何异常，检索会静默
返回无意义的相似度。查询向量缓存键因此包含 `(model, input_type, dim, text)` 四项，
同维度不同模型的缓存也不会互相命中。

某分区检索失败时（嵌入服务不可用、维度不符），其名称会写入响应诊断的 `degraded`
（形如 `vector:<模型名>`）；成功参与本次检索的分区列在 `vector_partitions` 里。
配置问题因此不会只躺在日志里，也不会表现为"结果莫名变少"。

回表这一步是新增开销，实测 6ms/300 个 uid，相对嵌入调用（1.5–3.5s）可忽略。

## 6. 迁移步骤（在线，无需重新嵌入）

1. 为现有主表补 `uid` 列（`add_columns` + 逐行 `update`，或整表重写）。
   8561 块实测 uid 生成 89ms。
2. 从主表 `vector` 列搬出一张分区表 `vec_<现役模型>_<dim>`。
3. 校验：分区行数 == 主表行数、uid 一一对应、抽样比对向量。
4. 切换代码路径到"分区检索 + uid 回表"，跑 55 条评测确认与基线一致。
5. `drop_columns(["vector"])`（确认 FTS 仍正常，已实测）。
6. 旧数据包（v1，单向量列）导入时自动转换为单分区格式。

全程不调用嵌入接口。

## 7. 实施顺序

三步走，每步独立可用、可回滚。

**第一步：结构就绪**
- 主表加 `uid`、去 `vector` 列；建现役模型分区；检索改走分区 + 回表。
- 此时功能与现状**等价**（只有一个模型），但布局已就位。
- 验收：55 条评测 recall/snippet 与基线一致；FTS 与子串通道不受影响。

**第二步：多模型与选择**
- ingest 支持写指定模型分区、`--rebuild-vectors`、`--drop-old-vectors`。
- `vector_models_priority` / `vector_models_exclude` 与降级/覆盖率。
- 验收：用第二个模型补建分区后，切换优先级结果随之变化；覆盖率正确显示。

**第三步：打包与界面**
- bundle v2：多分区 + 每分区 provider 信息；v1 包兼容转换。
- 前端：模型列表、覆盖率、重建入口、优先级/排除编辑。
- 验收：含两分区的包导出→导入往返一致（`tools/verify_roundtrip.py`）。

**追加：分区向量索引**（性能，见 §5.1）
- `vecstore.ensure_vector_index`：建 `IvfFlat(nlist=16)`；小库（<4096 行）拒绝。
- 查询侧按 `REFINE_FACTOR=2` 精算，只在有索引时生效。
- 写入/迁移路径建完分区自动建；`tools/build_vec_index.py` 补建。
- 验收：生产 55 条评测与建索引前完全一致；300 条查询 × top80 零漏召回。

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| uid 碰撞导致块互相覆盖 | uid 含页内块序；迁移时校验唯一性，不唯一则失败并报告 |
| 部分覆盖静默劣化 | 覆盖率进 `degraded` 与 `/api/stats`；设置页切换前校验 |
| 回表引入额外延迟 | 实测 6ms/300 uid；若 uid 很多，按 500 一批分次查 |
| 多模型分区体积膨胀 | 每模型 38MB（768 维）/ 203MB（4096 维）；NAS 剩余 857GB |
| 旧数据包无法导入 | bundle 带版本号；v1 自动转换为单分区 |
| 查询向量与分区契约错配 | 查询侧一律用分区记录的 model/dim/input_type_query，不用全局配置；缓存键含 model+dim+input_type |
| 部分块覆盖被误判为完整 | 覆盖率按块统计；`files_partial` 单独报告 |
| 重建误删数据 | `--drop-old-vectors` 默认关闭，且只影响目标模型自己的分区 |
| 索引替换后分区句柄失效 | 沿用现有 `library.reset_table()`，同时重置分区表缓存 |
| 单测写穿生产配置 | `tests/__init__.py` 把 `SETTINGS_FILE` 重定向到临时目录，测试不再落盘 |
| 向量索引静默漏召回 | 查询侧强制 `refine_factor=2`（rf=1 实测漏 17/400 条）；参数须按数据规模实测，不能按索引类型名假设"无损" |
| 小数据建向量索引反而错 | `MIN_ROWS_FOR_INDEX=4096`，低于则拒绝建（Lance KMeans 在 40 行上产出空簇，结果与暴力扫描全不同） |
| 增量写入后索引不覆盖新片段 | 每次写入结束重建索引（12421 行 0.5s） |
| 对暴力扫描误加 refine | 只在 `has_vector_index()` 为真时加 |

## 9. 已定与待定

**已定**（本轮确认）：

- **覆盖率按块统计**：向量化调用的输入单位是块（`embed_file` 逐块取向量），
  同一文件可能部分块有向量。按文件统计会掩盖真实缺口，故降级判定只看块覆盖率；
  文件覆盖率与"部分覆盖文件数"作为展示与调度参考一并报告。
- **input_type 必须进分区标识**：同一模型不同 `input_type_doc` 产出不同空间的向量，
  必须视为不同分区。查询侧按分区记录成对使用 `input_type_query`。
- 优先级与排除冲突时以**排除**为准（fail-closed）。

**待定**：

- 现役模型 slug 的具体归一化规则（模型名里的 `/`、`.`、`-` 都转 `_` 是否会撞名，
  例如 `a-b` 与 `a_b`）。倾向：保留原文的短哈希后缀兜底。
- 分区元数据放独立小表 `vec_meta`，还是写进各分区表的 schema metadata。
  倾向独立小表——可一次列出所有分区，避免逐个 open_table。
- 是否允许"按类别选模型"：不做，除非出现明确需求。

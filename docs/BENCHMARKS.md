# 评测与实验记录

集中存放检索质量评测结果、历次参数实验(含**否定性结果**)、上游服务行为实测与性能数据。
改参数、换模型、调排序之前先读这份——很多直觉按实测是错的,本文件就是防止重复踩坑。

- 口径:除特别注明外,均为 2026-10 生产环境(287 文档 / 12421 块,`qwen3-embedding-8b` @768 维,
  重排 `rerank-v4.0-pro`,Docker 于 NAS)。评测方法与指标定义见 README「评测」。
- 重排器有固有随机性,`snippet@1` 同代码重跑波动约 ±2pp;本文件标注"两次重复一致"的结果才可作为定论。

## 1. 检索质量基线

| 配置 | recall@5 | snippet@1 | snippet@5 |
|---|---|---|---|
| **当前默认**(片段宽 900 / 候选池 80 / 重排池 64) | **100%** | **62%** | **91%** |
| 旧默认(600 / 40 / 32) | 100% | 58% | 73% |

当前默认按来源拆分(两次重复运行逐条一致):

| 来源 | 条数 | recall@5 | snippet@1 | snippet@5 |
|---|---|---|---|---|
| hand(人工手写) | 10 | 100% | 80% | 90% |
| mined(自动挖掘) | 41 | 100% | 54% | 90% |
| topic(主题型) | 4 | 100% | 100% | 100% |

匹配规则与数据格式:

- `expect` 按**文件名**(正/反斜杠都认)子串匹配,与目录无关——类别目录会被重组,
  完整路径断言会把"检索其实找对了"误判成失败;expect 可列多份等价文档,命中任一即满分。
- `must_contain` 判定对空白/下标分隔符宽容("500 Ω" 命中 "500Ω")。
- `_` 前缀字段(`_page`、`_n_chunks_with_val`)是策展溯源信息,评测不使用;
  `tools/curate_eval.py` 从 `tools/mined_cases.json` + 内置手写用例重新生成评测集。

### 1.1 评测集本身曾有两处数据问题(已修)

- **反斜杠路径假阴性**:78% 的 `expect` 是早期 Windows 索引留下的反斜杠路径,而
  `os.path.basename()` 在 Linux 不认 `\`,43/55 条被自动判失败——recall 一度"看起来"只有
  22%。已改双向分隔符匹配并规范化数据。**教训:评测分数骤降先查匹配口径,再怀疑检索。**
- **`\t` 转义损坏**:一条查询的两条 expect 写了 JSON 单反斜杠 `\t`,被解码成制表符,
  长期未暴露是因为同查询还有第三条合法 expect 兜底。

### 1.2 准确率瓶颈归因(漏斗,旧参数下)

对 55 条查询逐级检查答案字面值出现在哪一层(页面文本取索引块拼接,即系统实际"知道"的内容):

| 层级 | 比例 |
|---|---|
| top-1 片段 | 58% |
| top-1 整页 | 67% |
| top-5 任一页 | 87% |
| top-1 整份文件 | 91% |
| 期望文件 / 全语料 | 100% |

23 条 snippet@1 失败的分类:**页级排序 ≈48%**(重排把"相关但无答案"的页排在答案页前,
含同族型号混淆)、**窗口定位 22%**(答案在页文本 1300–2000 字符处,600 宽窗口框不住)、
**候选池遗漏 ≈26%**(大手册答案页融合后进不了前 40)。**答案不在语料里的为 0**——提取与
OCR 不是瓶颈。修复③正是按这个归因定向做的。

## 2. 参数实验

### 2.1 ✅ 已采纳:片段宽 900 + 候选池 80(修复③)

| 变体 | snippet@1 | snippet@5 | 相对基线 |
|---|---|---|---|
| 基线(600/40/32) | 58% | 73% | — |
| 片段宽 900 | 62% | 85% | +4 / -2 |
| 细步长(div=8) | 58% | 82% | +3 / -3 |
| 参数值加分 2.5 | 58% | 82% | +3 / -3 |
| 池 80 | 58% | 87% | +3 / -3 |
| **组合(900 + 80/64)** | **62%** | **91%** | **+4 / -0** |

- "+3/-3 且修复集雷同"是**抖动信号**:片段参数会经 `rerank_on_window` 改变送重排的文本,
  从而扰动重排排序;单项测试的变化混杂抖动,组合后两次重复运行逐条一致才算定论。
- 代价:重排载荷 40→64 文档(约 +60% 延迟),换 18pp 的 snippet@5。

### 2.2 ❌ 已否决:召回名次 × 重排名次融合(`rerank_rank_weight`)

w∈{0.5, 1, 2} 全部差于基线:snippet@1 38% / 38% / 49%(基线 58%),**零修复、破坏 5–11 条**。
被破坏的清一色是参数值类查询(TPS55289 纹波、TPS63020 开关频率)——这些查询上重排器的
语义判断本来是对的,混入 RRF 词频共识后概述页反而抢走 top1。**重排分 0.8–0.95 挤在一起时,
任何与词频信号的混合都会让关键词密度高的页占优。** 代码保留为开关(默认 0)。

### 2.3 ❌ 已否决:型号平局裁决(`rerank_tie_tolerance`)

相邻页重排分差小于阈值时,查询型号与文件身份匹配者在前。tol=0.05 与基线逐条一致,
tol=0.02 破坏 1 条。失效原因:有同族抢占问题的查询(Quectel)**本身不含型号**,裁决无从
触发;含型号的失败其实是同文件内页序问题。代码保留为开关(默认 0)。

### 2.4 ❌ 已否决:查询侧 instruct(Qwen3 官方建议)

官方模型卡称查询侧不加 instruct 掉 1–5%。实测(英文/中文指令,文档侧不加):向量确实改变
(cos 0.897),但 snippet@1 仅 +1 条、snippet@5 +1~2 条;两次无指令基线**完全一致**,故 +1
是真实的但幅度远低于宣称值。不值得为此改嵌入契约与数据包格式。

### 2.5 ❌ 已否决:嵌入维度 768 → 4096

- 关系:上游返回的 768 维就是 4096 维的 **MRL 截断**(实测 cos=0.99993),前 768 维仅占
  向量总能量 19%——看似损失巨大,实则:
- 排序确实不同(top-10 重合率均值 77.8%、Spearman 0.576),但**期望文件的名次在两个空间
  完全相同**(recall 已 100% 饱和,向量通道只需把正确文件送进候选池);
- 代价:4096 维嵌入**慢 17 倍**(0.8 vs 14.2 块/s,全量重建约 2 小时),索引 43MB→约 230MB。
- 结论:768 维够用。`embed_dimensions` 已显式固定为 768,不依赖上游默认值。

### 2.6 ❌ 已否决:更换嵌入模型

各候选模型对同一子集(4646 块 = 2146 期望块 + 2500 随机)自建索引、同 25 条查询:

| 模型 | 维度 | recall@10 | 名次中位 | MRR | 索引耗时 |
|---|---|---|---|---|---|
| cohere-v4 | 1536 | 100% | 1 | 0.966 | 727s |
| cohere-v5-pro | 2048 | 100% | 1 | 0.948 | 3046s |
| nemotron-3-embed-1b | 2048 | 100% | 1 | 0.944 | 500s |
| **qwen3-embedding-8b(现状)** | **768** | **100%** | **1** | **0.900** | 2830s |

全部饱和,MRR 差 ≤0.066(约等于 1–2 条查询的第一名变第二名,与重排抖动同量级)。
换模型只有更大的索引(2–2.7 倍维度)、全量重建与契约重绑,没有准确率回报。
通用榜单上 Qwen3-8B 已非第一(2025-06 MTEB multilingual 第一 70.58;后有 Octen、
WeMM、Cohere v5 等),但在**本服务商可用模型里没有实测更优的选项**。

### 2.7 ✅ 批量无截断(维持 batch=32)

担心过 32×1500 字符的中位批量(33k 字符,p90 63k)会超出模型上下文被静默截断。实测把
3144 字符长块分别单独嵌入、放进 8/16/32 块批次的**首位与末位**,余弦相似度全部 ≥0.9999
(纯数值噪声)。上游不截断,当前批量安全。

## 3. 上游服务行为实测

### 3.1 重排器是**非确定性**的(嵌入基本确定)

- 同一请求连发:分数微抖(单文档波动中位 0.00127、最大 0.0039);
- 40 个候选中 **12 对相邻名次**的间隔小于抖动幅度,先后本质随机;
- 同请求 10 次:仅 5 次排序完全一致(共出现 4 种排列),但 **top-10 集合 10/10 稳定**;
- 这就是 `snippet@1` ±2pp 波动的根源。对策:接受抖动,靠评测重复运行与粗粒度判断;
  已否决"多次调用取中位"(成倍调用量换不动 top-10 集合)。

### 3.2 重排器没有会话概念

逐个试过 `session_id` / `conversation_id` / `user` / `metadata` / `seed`,上游全部 HTTP 200
(吞掉未知字段)。决定性证据:**同一 session 连发两次的差异(0.003905)= 不同 session 之间
的差异 = 不带 session 的差异**;单文档请求也有抖动。分数差异来自推理非确定性,与会话无关。
嵌入接口同理,是无状态纯函数——**本项目不需要任何会话 ID**。

### 3.3 嵌入延迟特征

单次查询嵌入 1.5–3.5s,抖动 1.3–7.0s,与维度(768/1024/2048)、文本长度(6–36 字)均无关,
纯上游波动。缓存后二次为 0ms(查询向量 LRU + 结果缓存)。项目口径:**延迟不是优化目标,
准确性优先**。

### 3.4 服务商可用嵌入模型(2026-10)

qwen3-embedding-8b、embed-v3/v4.0/v5.0(pro+fast,Cohere 系)、nemotron-3-embed-1b、
lfm-2.5-embedding-350m、llama-nemotron-embed-vl-1b-v2。注意:Cohere 系**强制要求
`input_type`**(不带直接 400),配置里的 `embed_input_type_doc/query` 就是为它们预留的。

### 4.1 代码级优化实测(回退会明显变慢)

| 位置 | 做法 | 实测原因 |
|---|---|---|
| `library.scan_arrow` | 投影下推 `search().select(cols).limit(count_rows())` | 直接 `to_arrow()` 会把 768 维向量列(26MB)也读进内存再丢:54ms → 16ms |
| `main._table` / `server._get_table` | 只比对 `table.version` | 曾用 `to_arrow().num_rows` 探测句柄,等于每请求物化全表(37ms) |
| `library.cached` | 元数据按 `table.version` 缓存 | `/api/files`、`/categories`、`/extract/report` 各扫一遍全表,实际只在 ingest 后变化 |
| `/api/files` 聚合 | `if k not in seen` 而非 `setdefault` | `setdefault` 的默认 dict 每行都构造,让 `product_label` 正则跑满每块(20ms → 1ms) |
| 前端 `getSWR` | 切回页面先用上次结果、后台刷新 | 每次进入都全量重拉是纯开销 |
| `SelectiveGZip` | JSON 压缩,跳过 `/mcp`(SSE)与 `/api/pdf`(已压缩) | JS bundle 708KB 裸传 → gzip;`/api/files` 59KB → 9KB |
| 索引碎片整理 | `tools/compact_index.py` | 长期增量后 248MB/517 版本 → 43MB/8 版本,行数与检索结果不变 |

### 4.2 纯逻辑路径(不含模型调用)

`tools/bench_logic.py`:把 `embed_query` 与 `_call_reranker` 换成确定性本地替身,
其余代码一行不改,测"本系统地带的计算成本"。零网络、零 API 额度、可复现。
**它测的不是端到端延迟** —— 真实查询里嵌入 1.5–3.5s、重排 0.5–1.6s 完全压倒这部分。

本机 8561 块 / 768 维,单分区:

| 阶段 | 中位 | 说明 |
|---|---|---|
| FTS 检索(limit 80) | 2.7 ms | 有 FTS 索引 |
| 子串召回 | 17.9 ms | 全表 `pc.match_substring`,每查询一次 |
| 子串投影表冷建 | 19.4 ms | 每进程一次,之后命中缓存 |
| **向量检索(limit 80)** | **23.6 ms** | **分区表无向量索引 → 暴力扫描** |
| 回表 `_hydrate`(80 uid) | 2.0 ms | 与块数无关 |
| 覆盖率(缓存未命中) | 15.6 ms | 扫全分区 uid,每版本一次 |
| 元数据 `files_index` | 20.9 ms | 缓存未命中时 |
| 元数据 `extract_report` | 50.4 ms | 含 text 列物化 |
| `make_snippet`(1443 字符块) | 0.07 ms | 窗口打分,成本可忽略 |

> 下列整组数字测于**建向量索引之前**(向量检索 23.6ms = 暴力扫描)。
> 建索引后向量通道降到 12.5ms,完整检索的热态随之从 44.6ms 降到 34.1ms;
> 详见 §4.3。

完整 `search()`(mixed + rerank,替身重排):

| 档位 | 冷(首条查询) | 热(缓存就绪) |
|---|---|---|
| mixed + rerank | 102 ms | 44.6 ms → **34.1 ms** |
| mixed,无重排 | 89.6 ms | 37.4 ms → **27.2 ms** |
| 仅 FTS + 子串 | 43.9 ms | 3.4 ms |
| 仅向量 | 52.2 ms | 37.1 ms → **24.7 ms** |

冷热差 = 投影表(19ms)+ 覆盖率(16ms)首次构建,只付一次。
结果缓存命中 0.09 ms;55 条查询全量走一遍中位 62 ms → **51 ms**、p95 102 ms。

## 4.3 向量索引(已实施)

原先分区表没有向量索引,每次检索扫全表。建索引后:

| 环境 | 暴力扫描 | 索引 + refine | 提升 |
|---|---|---|---|
| 本机 8561 块 / limit 80 | 26.3 ms | 12.5 ms | 2.1x |
| 本机 limit=1 | 17.2 ms | 2.3 ms | 7.5x |
| **生产 12421 块 / limit 80** | **59.9 ms** | **32.8 ms** | **1.83x** |

索引构建 **0.3–0.5 秒**(12421 行),在整轮索引里可忽略。

### 参数与"无损"的边界

`IvfFlat(nlist=16)` + 查询侧 `refine_factor=2`。两个参数都必须实测:

| 变体 | top80 相对暴力扫描 |
|---|---|
| nlist=16, rf=1(默认) | 700 条查询漏 17 条,**召回 0.99947** |
| **nlist=16, rf=2** | **漏 0 条,召回 1.0**(300 条查询 × top80 严格审计) |
| nlist=16, rf=4 | 同样 0 漏,仅多花时间 |
| nlist=128, rf=2 | 78/80 |
| nlist=256, rf=2 | 73/80 |
| HnswFlat m=4 efC=10 | 78/80 |

`refine_factor` 的作用:IVF 只搜最近的一小部分簇,真实近邻可能落在没搜的簇里。
rf=2 让索引先取 2×k 个候选,再对这批做精确距离重算,把漏的捞回来。

**"无损"是参数与数据规模共同决定的结果,不能按索引类型名假设。** nlist 越大,
每簇行数越少,同样的探测预算下漏得越多。

### 数据量下限

Lance 的 KMeans 在小数据上会产出大量空簇。实测 **40 行**建索引后 top10 与暴力
扫描**无一相同**(Lance 自身警告 `40 < 4096`)。因此代码里有
`MIN_ROWS_FOR_INDEX = 4096`:低于该行数拒绝建索引,直接走暴力扫描(几千行本来
也只要 20ms 上下)。这个门槛是**正确性保护**,不只是性能取舍。

### 端到端验证

- 生产 55 条评测:recall@5 100% / snippet@5 91% / snippet@1 62%,**与建索引前完全一致**
- 本机 25 条查询:有索引 vs 无索引,最终 top5 **零差异**
- 300 条查询 × top80:索引结果相对暴力扫描**零漏召回**

唯一观测到的差异在 top20 的第 19/20 名边界(查询向量恰是库内某行自身时),
被 RRF 与重排完全吞掉,不改变最终结果。

### 兼容性

索引是**可选加速**:老索引库没有它照样能查(退化为暴力扫描)。查询侧只在
`has_vector_index()` 为真时才加 `refine_factor` —— 对暴力扫描加强化行为未定义。
补建入口:`python tools/build_vec_index.py`(已建则跳过,`--rebuild` 强制重建)。

> **`_distance` 不能跨路径比较**:同一向量在暴力扫描下给出 `0.3284`,在索引下
> 给出 `0.1642`,比值恒为 0.5。手算 `1-cos = 0.164189` —— 索引值才是对的,
> 暴力路径返回的是它的两倍。排序不受影响(单调变换),但拿 `_distance` 做阈值
> 判定时必须知道当前走的是哪条路径。

### 4.4 OCR 内容筛选的离线对照（2026-10-23）

`tools/audit_ocr_policy.py <PDF 根目录> --output <新文件.json>` 逐文档比较“单页原生文本
不足 200 字就 OCR”与 `ocr_policy.DocumentPolicy`。不调用任何 OCR/嵌入/重排模型，
不运行 ingest、不写索引。NAS 对照只在独立进程内加载候选代码，未改部署文件或重启服务。

| 语料 | PDF / 页 | 原字数策略候选 | 新策略候选 | 免除比例 |
|---|---:|---:|---:|---:|
| 本地语料 | 246 / 9444 | 438 | 426 | 2.7% |
| NAS 全库 | 286 / 10408 | 563 | 516 | 8.3% |
| NAS 中 Tastek 子集 | 39 / 891 | 124 | 89 | 28.2% |

NAS 免除的 47 页为 33 张封面、14 张稀疏正文/章节页；Tastek 子集是 33 张封面与
2 张简短正文。查看了全部免除页的原生文本和渲染总览，并对正文边界样例检查完整渲染；
33 张封面保留标题、版本、日期，正文样例的原生内容与现有索引对照，没有发现缺失正文。
寄存器页仍执行原表格提取，不能把原生字符数与“含 markdown 表格”的入库字符数直接比较。
93 张零文本页全部保留 OCR；SHT4x 等连续缺少正文文本的文档不被免除。

**水印是面积判据的反例**：Tastek 部分正文里的最大图片是跨页复用的浅色斜向水印，
并非操作截图。移除水印干扰后，有些页只有简短原生文字，有些页仍有独立截图；
重复、面积大或位置在首尾都不能单独作为免除依据。

最终 NAS 单进程串行判定约 32.3s，其中全文文本画像约 27.3s，余下结构判断约 5.0s；
本机约 15.0s，其中画像约 14.0s。画像中的原生文本在真正提取时复用，不能把整个画像
时间都当成新增开销；但按需读取一个低文本页需要建立文档上下文，大手册可能多付秒级成本。
这些数字受文件缓存、硬件及 PDF 原生库影响，不是端到端索引提速数据。

**边界**：这是减少候选请求数的离线证据，不是 OCR 输出等价或检索质量无损的证明；
没有重新请求模型，没有重建生产索引，因此不声称召回率不变或总耗时按同比例下降。
开关 `ocr_smart_filter=false` 可回到原字数策略，规则设计见 `ARCHITECTURE.md` §5.1。

### 4.5 解析进程与 OCR 通路（2026-10-24）

**CPU/渲染侧实测**：NAS 为双核四线程 i3-7100。39 份 PDF / 891 页，保留真实文本、
表格、分块和 89 张候选页的 200 DPI PNG 渲染，OCR 替换为本地返回且阻止网络连接。
显式 spawn、低优先级，按 1/2/4/8/8/4/2/1 顺序运行，包含进程启动：

| 本地解析进程 | 平均耗时 | 基准进程组峰值 PSS（不含常驻后端） |
|---|---:|---:|
| 1 | 100.9s | 0.74 GiB |
| 2 | 57.9s | 1.21 GiB |
| 4 | 54.5s | 2.01 GiB |
| 8 | 63.8s | 3.23 GiB |

所有轮次的文本与分块哈希相同。双核机器从 4 加到 8 反而慢 16.9%，不能将该结论
推广到更多物理核的用户机器，因此 `extract_workers` 仍可独立配置（1–32）。
文件级并行无法消除单文档 OCR 串行拖尾：此批 89 页中最大文件独占 23 页。

**独立 OCR 通路替身验证**：单份 20 页合成 PDF、本地解析进程固定 1，每个识别替身
固定等待 120ms；真实执行 spawn、渲染、队列、表格、结果收集，未请求任何模型。
1/4/8/8/4/1 两轮均值为 3.31s / 1.43s / 1.18s；峰值同时识别数严格为 1/4/8，
每轮调用 20 次且分块输出完全相同。另有两文档/两解析进程测试，验证 OCR 总并发为
配置值而非乘积、单页失败保留原生文本、坏 PDF 不丢其他文件、临时图清理及乱序恢复。

这些数字证明调度路径能利用独立通路，不代表真实 OCR 延迟或服务商能承受的并发量。
配置面板在隔离临时配置环境中实际保存 OCR 并发 8，刷新仍为 8，本地解析进程仍为 4；
未改线上设置，也没有运行生产索引。架构与生效边界见 `ARCHITECTURE.md` §5.2。

## 5. 安全与路径实测

- **路径穿越**:`/api/pdf`、`/api/page`、MCP 读页、强制重索引入口均经 `resolve_under()`
  防护。实测 `file=/etc/passwd`(join 遇绝对路径丢前缀)与 `../..` 均被拒(404 / 明确报错),
  正常相对路径不受影响;反斜杠分隔符先归一为正斜杠再校验(拦截混合分隔符穿越)。
- **file 过滤语义**:DataFusion 的 LIKE 里 `_`/`%` 是通配符(实测 `BH1750FVI_TR` 曾命中
  `BH1750FVI-TR`),与 Python 兜底判定的字面语义不一致。已改为字面匹配 + 分隔符归一:
  Windows 风格输入(`01_传感器\X.PDF`)从静默 0 条变为正常命中。

## 6. 测试方法学

1. **改排序/片段相关代码前后各跑两遍评测**,只把"两次重复一致"的差异当结论;
   单次 ±2pp 内的变化不作为依据。
2. 输出里 `degraded` 必须为空,否则该次分数被限流污染,不代表代码水平。
3. 评测脚本自动关结果缓存(`override_local`,不持久化);**必须在独立进程跑**,
   别在常驻服务进程内热插拔配置后直接评测。
4. 纯向量通道的召回用 `--mode vector --no-rerank` 隔离观察;端到端结论以 mixed+rerank 为准。
5. 网格搜索看到"+3/-3 且修复集雷同"= 抖动重采样信号,不是真实收益。
6. 换嵌入模型/维度/输入类型 = 全量重建 + 数据包契约重绑,动手前先看本文件 §2 的否定性结果。
7. **测缓存类路径要绕开预热**:通用 `bench()` 的 warmup 会把投影表/覆盖率缓存填上,
   冷建成本会被测成 0.1ms(实际 19ms)。冷建必须显式清缓存且跳过 warmup。
   同理,测"稳态查询"要清结果缓存、但**不能**清投影表与覆盖率缓存,否则测的是
   每条查询都全表物化 —— 线上只有进程启动后的第一条付这笔钱。

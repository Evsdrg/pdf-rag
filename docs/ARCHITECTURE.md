# 架构设计

本文说明系统**为什么这样分层、每个边界守什么约束**。具体参数取值、实测数据、操作步骤
不在本文展开——那些属于 [BENCHMARKS.md](BENCHMARKS.md)、[DEPLOY.md](../DEPLOY.md) 与
[VECTOR-PARTITION.md](VECTOR-PARTITION.md)。

目标读者：要改代码、加功能、或评估这套系统能否满足新需求的人。

## 1. 一句话定位

对本地元器件手册库（PDF/Markdown）做**三路混合检索**，把"文档级命中"细化到
"页内哪一段含答案"，并通过 Web / MCP / REST 三种入口对外提供**同一套**能力。

它不是一个通用 RAG 框架：语料是**器件手册**（结构化强、型号密集、表格多），
检索目标不是"找相关文档"而是"定位参数值在哪一页的哪一段"。整个设计围绕这个目标。

## 2. 分层与依赖方向

```
 入口层      web/ (Vue)        server.py (MCP)      clients/pi (REST 示例)
                 │                    │                      │
                 └────────┬───────────┴──────────────────────┘
                          ▼
 传输层      backend/main.py (FastAPI, 28 端点)   ← 只做 参数→调用→序列化
                          │
                          ▼
 领域层      backend/library.py   ← 读页/精确检索/元数据聚合,与传输无关
             backend/retrieval.py ← 检索核心
             backend/vecstore.py  ← 向量分区
             backend/bundle.py    ← 数据包
                          │
                          ▼
 基础层      backend/config.py (配置中心)  doc_utils.py (PDF/MD 提取)
             backend/ocr.py (OCR 抽象)     LanceDB（外部存储引擎）
```

**依赖只能向下**。三条硬规则：

1. **领域层返回 Python 原生结构，不返回 JSON 字符串**。序列化交给传输层；可预期错误
   抛 `LibraryError` 子类（带 `status`），由 MCP 转成 `{"error":...}`、HTTP 映射成 4xx。
   这条规则来自一个实际教训：`read_page` 曾在两侧各写一份，错误文案靠人工对齐，
   后来出现行为漂移。
2. **MCP 与 HTTP 共用 `library.py`，不各自实现**。`MCP_INPROC=1`（默认）时两者同进程，
   连连接与表句柄都共享同一份单例。
3. **`vecstore` 依赖 `library`，不反向**。表名列表这类薄工具放在 `library`，
   因为 `vecstore` 已经用它的 `scan_arrow`，反向导入会成环。

## 3. 检索流水线

三路召回各自产出候选（代码里是顺序调用，但彼此独立、互不依赖），再统一融合：

```
query
 ├─ FTS        主表 text 上的全文索引          → 候选(带 rank)
 ├─ 子串        主表 text 全表 match_substring  → 候选(bonus rank)
 └─ 向量        按优先级选分区 → 分区内向量检索  → 命中 uid → 回主表取元数据
                （分区有索引时追加 refine_factor）
        ↓
   RRF 融合（页级累加计分）
        ↓
   跨版本去重（同文档只留版本号最高的一份）
        ↓
   重排（可选，服务商 reranker）
        ↓
   片段定位（查询感知窗口）
```

### 3.1 为什么是三路，而不是只留一路

各有不可替代的盲区，实测证据见 [BENCHMARKS.md](BENCHMARKS.md) §1：

| 通道 | 不可替代之处 |
|---|---|
| 向量 | 语义相近但用词不同（"供电电压" vs "VDD range"） |
| FTS | 精确词、多语言；有索引、快 |
| 子串 | **FTS 对型号前缀有盲区**：查 `W25Q32` 在 FTS 里命中 0 块，而文档写的是 `W25Q32JW`，子串能命中 82 块 |

所以子串通道虽然最贵（全表扫描），**不能砍**。它唯一的职责就是这个前缀匹配。

### 3.2 计分是页级的，不是块级的

同一页的多个块得分**累加**。这是刻意的：同页多块命中是有效的相关性信号。
改成块级独立计分会让正确页被邻近页顶掉（实测回归）。

代表块取"该页自身得分最高的块"，不是页首块——页首块几乎不含答案。

### 3.3 片段是"页内定位"，不是"截断"

手册的答案（参数值）常在中段或表格里，页首数百字符恒为页眉 + 章节标题。
所以片段取**查询感知窗口**：在该页所有命中块上滑动打分，选最相关的一段。

两个反直觉的取舍：

- 型号 token **不参与**窗口定位。它每页页眉都出现，对"页内哪一段"无区分度，
  反而会让含页眉的窗口压过含参数值的窗口。
- 中文按 2-gram 切分。否则"发送功率电流"必须逐字命中，而文档写作"发送功率"。

### 3.4 去重的硬前提是型号一致

厂商常用一份手册覆盖整个料号族，或同一文档有多个版本。合并判据按强度排列：
**内容 md5 相同** → 同一文档；否则**型号必须一致**才能谈版本合并。

不能只凭标题指纹：不少中文 PDF 的元数据标题就是章节名，实测三份不同型号的手册
标题都是"主要特点"，仅凭标题会把它们并成一组、只留版本号最高者，其余型号被静默删除。

### 3.5 降级必须响亮

每一路失败都往 `diagnostics["degraded"]` 写一条，最终体现在响应的 `notice` 里。
不这么做的话，上游限流或配置错误表现为"结果莫名变少"，而调用方以为一切正常。

## 4. 向量存储：按模型分区

主表 `chunks` **不含 vector 列**，向量放在 `vec_<slug>` 分区表。原因与完整设计见
[VECTOR-PARTITION.md](VECTOR-PARTITION.md)，这里只给三条结论：

- **一个块一个模型**是数据粒度，**一个模型一个分区**是存储粒度。分区可以只覆盖部分块。
- **查询向量必须与该分区的契约成对**：用分区记录的 `model + dim + input_type_query`
  生成，不能用当前全局配置。三者任一不匹配都是跨向量空间检索。
- **分区间绝不混算距离**。一个块在多个分区都命中时只计一次（按 uid 去重），否则
  "被多个模型索引过的块"会凭空获得权重优势。

## 5. 索引构建流水线

两个阶段用不同的并发模型，因为瓶颈性质不同：

```
扫描 → 计划（md5 未变的跳过）
   ↓
阶段一 提取   ProcessPoolExecutor × extract_workers（spawn）
         同时处理不同 PDF：原生文本 + 表格 markdown + 页面渲染
         （find_tables 有进程级可变状态，不在线程间共享）
                ↓ 有界图片队列
         固定 OCR 通路 × ocr_workers（整轮共用，连接各自复用）
                ↓ 按文件/页码回收，原生文本与 OCR 比较后恢复页序
   ↓
阶段二 嵌入   ThreadPoolExecutor × embed_workers
         批量请求（线程足够：等的是网络）
         ↓
      主线程按序写库：主表（元数据+文本+uid）+ 当前模型分区
```

**uid 是贯穿两侧的锚**：`sha256(file \x00 page \x00 block_seq)[:20]`。
**text 不参与哈希**——实测 8561 块里有 9 个同页逐字相同的块，把 text 算进去会互相覆盖。

增量语义：只处理 md5 变化的文件，且**只写当前模型的分区**。所以换模型后点增量索引，
效果就是"只给新模型补缺失的块"，旧模型的分区原样保留。

## 5.1 低文本页的 OCR 判定

`ocr_min_chars` 是候选线，不是“文字缺失”的充分条件。`ocr_policy.DocumentPolicy`
先提取整份 PDF 的原生文本，得到低文本页占比、连续段与字数分布；后续复用这些文本，
不重复做文本提取。入库与按需读页共用此模块，多页读取在同一个 Document 内复用判定。
普通高文本单页读取不扫描全文；低文本单页读取需要为上下文付一次全文预扫描成本。

规则偏向保留 OCR：

- 零文本、少于四页的短文档、低文本占比超过一半、连续至少四张低文本页，保留 OCR。
- 原生有效字符过少、乱码、仅页面边缘有文字、注释/表单、图像归属不明确或检查失败，
  保留 OCR。比例低不代表个别截图页可免除。
- 图片只能在有额外装饰证据时忽略：相同资源至少在三页且覆盖 60% 页面，抽样放置一致；
  小型页眉页脚标识，或带软遮罩、斜向放置且全分辨率像素均为浅色的水印。
  同尺寸多资源不能确定归属时保留 OCR；深色重复图片不会仅因重复被忽略。
- 复杂矢量、曲线与正文填充形状保留 OCR。少量横竖表格线和页边细分隔线允许通过，
  但原有 `find_tables` 与 markdown 表格提取不跳过、不改策略。
- 只有排除了上述缺失迹象且页面中央仍有可读文字的稀疏页，保留原生文本而免除 OCR。

`ocr_smart_filter=false` 可恢复仅按字数触发。规则常数是保守首版边界，不是分类准确率承诺；
离线审查入口为 `tools/audit_ocr_policy.py`，输出决策原因及所有被免除页面的原生文本，
不调用 OCR、不请求嵌入/重排、不写索引。提取过程将 OCR 用量、决策原因计数与质量告警
写入 `run_state.json`；这不是持久化提取缓存，重建容器可能丢失该状态。

策略改变不自动重提取旧文档；MD5 不变仍按原增量语义跳过，需由用户显式指定文件重跑。

## 5.2 两层并发与资源边界

本地解析一直以文件为任务，`extract_workers` 控制同时处理多少份文档；不是一个进程
逐文件包办全库，也暂不将单文档的 CPU 工作切为页段。OCR 则改为逐页投递，
`ocr_workers` 是整轮索引共用的请求通路数，同一份 PDF 可使用多个空闲通路，两项不相乘。
两项默认均为 4，范围 1–32，由 Web「配置中心 → 索引与并发」独立调整。

解析进程使用 `spawn`，不继承已经启动的 LanceDB/HTTP 线程与原生句柄；父进程把本轮
可调参数快照传给子进程，避免测试或临时覆盖在 spawn 后丢失。密钥仍从环境读取，
不进入配置快照。运行中的任务不动态扩缩容，保存并发设置在下一轮索引生效。

`ocr_queue` 只有一个请求队列、每个解析进程一个响应通道，以及固定数量的请求线程。
各通路只接收图片路径，不接触 Document/Page；图片先在原解析进程渲染，表格提取也
留在该进程。渲染前先取得容量许可，渲染中、排队与请求中的图片合计不超过
`2 × ocr_workers`；完成即删除图片并释放许可。响应及时回收，不等待整份 PDF
渲染完才读取；最终按原页序分块，异步完成顺序不改变页码或页内块序。

通路各自复用一个 HTTP 客户端。OCR 错误按页记录并保留原生文本，单个文档提取异常
写入本轮 errors 而不丢弃其他成功文件。读页 API 沿用直接调用，不在索引池的全局额度内。
提取与嵌入仍保留原有阶段边界，没有引入嵌套进程池、动态优先级或跨阶段复杂调度器。

## 6. 配置分两层，边界是密钥

| 层 | 内容 | 改动生效 | 存储 |
|---|---|---|---|
| 环境层 | 密钥、根目录、服务地址、模型名 | 需重启 | `.env` |
| 可调参数层 | 检索融合、片段、排序、缓存、提取阈值、OCR 后端与并发 | 检索即时；索引任务在启动时读取快照 | `data/settings.json` |

**密钥只存在于环境层**：`EMBED_API_KEY` / `OCR_API_KEY` / `ADMIN_TOKEN` 绝不写入
配置文件、数据包、或返回给前端。这条边界在 `config.py` 里体现为环境类常量与
`Spec` 注册表两类，前者不进 `snapshot()`。

`set_many()` 会把覆盖值落盘，而 `data/settings.json` 在容器部署里是 bind mount 的
**线上配置文件**——所以测试必须重定向 `SETTINGS_FILE`（见 `tests/__init__.py`）。

## 7. 不做什么

这些是刻意的设计约束，看起来像缺失，实际是决定：

| 不做 | 原因 |
|---|---|
| **不主动探测上游服务可用性** | 定时探活会给服务商带来无意义负载。OCR/嵌入的状态只反映**最近一次真实调用**的结果 |
| 不缓存降级结果 | 降级可能是接口暂时故障，缓存住会让问题持续整个 TTL |
| 不为每个模型单独建 FTS | FTS 与模型无关，留在主表 |
| 不在同一次距离计算里混合不同模型的向量 | 向量空间不可比，相似度无意义 |
| 不做全自动重排调参 | 重排器有固有抖动（相邻名次分差可能低于抖动幅度），单次差异不作为依据 |

## 8. 关键不变量

改代码时这些不能被打破：

1. **`uid` 唯一且稳定**：`(file, page, block_seq)` 决定，与文本无关。分区行靠它回表。
2. **主表与分区通过 uid 一一对应**；主表已无的 uid（孤儿）必须被丢弃而非报错。
3. **查询向量与该分区契约成对**，三者（model/dim/input_type）缺一不可。
4. **缓存键必须覆盖全部影响结果的参数**：`_CACHE_PARAM_KEYS` 里的 24 个可调项
   + 表版本 + 分区版本。漏一个就会出现"改了设置但结果不变"。
5. **路径一律经 `resolve_under()`**：`os.path.join` 遇绝对路径会丢弃前缀，
   不做校验等于允许读任意文件。
6. **子串/向量过滤是字面语义**，不是 SQL LIKE 语义（`_`/`%` 在 LIKE 里是通配符）。

## 9. 扩展点

按改动量从小到大：

| 需求 | 做法 |
|---|---|
| 加一个检索参数 | `config.py` 加 `Spec`，注意同步加入 `retrieval._CACHE_PARAM_KEYS` |
| 加一个 HTTP 端点 | `main.py` 加路由，逻辑放 `library.py`（MCP 也能复用） |
| 换嵌入/重排模型 | 改环境变量；旧向量仍可用（分区按模型隔离），新文件走新模型 |
| 加一种文档格式 | `doc_utils.py` 加读取器 + `ingest.iter_pdfs` 的后缀列表 |
| 加一个 OCR 后端 | `ocr.py` 加分支，参数走 `config` 的 OCR 组 |
| 加一个客户端 | 参考 `clients/pi/`：REST 或 MCP 均可，能力等价 |
